商品页改稿台 · 团队版

按 SKU 写英文标题与五点，每条注明依据，双人复核后导出

商品页改稿最容易出的问题不是英文不好，而是文案里写了资料上没有的东西：尺寸、材质、适用场景没人能指回规格单。这个工作台要求每条标题和卖点都挂一条依据，指定同事批准后才能导出。

打开团队版 看搜索词体检样例 看配套的广告工具

私有站点：团队版只对站点授权账号开放，演示前需要在站点访问设置里给对应账号开通权限。不能直接公开访问。

01角色与流程

  1. 编辑新建稿件

    填写 SKU、目标站点 / 语言、另一位同事的登录邮箱，以及商品事实与来源（规格单号、验收记录）。

  2. 写标题与五点

    六块内容逐条填写：标题 + 五条卖点。每条都有一栏“商品资料依据”，留空不能提交复核。

  3. 提交复核

    稿件进入待复核，只有被指定的复核人能批准或退回；退回必须写明理由。

  4. 批准与导出

    批准后的版本才能下载 TXT；运营拿到文件后自行上传销售平台，系统不直接改线上商品页。

  5. 重新修订

    编辑可开启下一版本；上一版批准自动失效，修改后必须重新复核。

02权限与版本

只看自己的活

工作台只列出本人创建或被分配复核的稿件。其他账号直接访问稿件地址会返回 404，不暴露标题或内容。

版本冲突拦截

每次写入带当前版本号；两人同时改，后提交的一方收到冲突提示并要求重新载入，不会静默覆盖。

历史快照

创建、提交、退回、批准、重开都会写入版本记录，保留当时的商品资料、六条文案和复核意见。

同事务写入

版本快照与稿件更新在同一个数据库事务里完成，不会出现“内容更新了但记录没留下”。

03AI 起草的边界

“用 AI 起草”不会在站点内直接调模型，也不会自动改稿。编辑下载一份基于当前商品资料的提示词，交给公司批准的 AI 工具，再把返回的六组 JSON 粘回来。

  • 返回必须正好六组文案与依据；缺项、空值或格式不符直接拒绝填入。
  • 填入后仍是草稿，编辑要逐条核对；提交复核时每条依据仍必填。
  • 提示词把商品资料和原稿都声明为数据，要求只采用可核实事实；拿不准的写成“待核对”。

04验证与运行

测试脚本在内存 SQLite 上执行项目自带的建表迁移，调用真实的 Worker 路由，模拟编辑和复核人两个身份，覆盖 9 组验收：未登录拒绝、重复创建、必填校验、退回必须写理由、版本冲突、批准、导出、重开与审计记录。

node test.mjs    # 双身份端到端验收
node build.mjs   # 生成 dist/server/index.js
  • 运行时为 Node 22.13+，身份与数据由站点托管环境提供（Sites 身份 + D1）。
  • 身份由站点代理注入；不要把接受任意身份请求头的 Worker 直接暴露在没有身份代理的自建服务器上。
  • 上线前需用公司账号做双人验收，确认员工访问范围和商品资料存储要求。
